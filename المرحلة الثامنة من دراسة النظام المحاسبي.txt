## 1. فلسفة DevOps و SRE

### 1.1 الفجوة التاريخية

```
قبل DevOps:
  Developers ──── يكتبون كود ──→ يرمونه على الحائط
                                         ▼
  Operations ──── يحاولون تشغيله ──→ يفشل في الإنتاج
                                         ▼
                  لوم متبادل، صراع، بطء، حوادث
```

### 1.2 فلسفة DevOps

> **Development + Operations = فريق واحد، هدف واحد، أدوات واحدة.**

#### المبادئ الأساسية (CALMS)

| Letter | المعنى |
|--------|------|
| **C**ulture | ثقافة التعاون |
| **A**utomation | كل ما يمكن أتمتته، يُؤتمت |
| **L**ean | تقليل الـ waste |
| **M**easurement | كل شيء يُقاس |
| **S**haring | معرفة مشتركة |

### 1.3 SRE (Site Reliability Engineering)

> ابتكرته Google. **"المشغّلون يكتبون كود لأتمتة عملهم."**

#### مبادئ SRE
1. **Embrace Risk** - 100% reliability مستحيلة ومكلفة
2. **Service Level Objectives** - حدد ما هو مقبول
3. **Eliminate Toil** - أتمت العمل المتكرر
4. **Monitor Everything**
5. **Automate** - الإنسان للقرارات، الآلة للتنفيذ
6. **Release Engineering** - النشر علم
7. **Simplicity** - البساطة = موثوقية

### 1.4 المقاييس الذهبية لـ DevOps (DORA)

| المقياس | Elite | High | Medium | Low |
|--------|------|------|--------|-----|
| **Deployment Frequency** | عدة مرات/يوم | يومياً-أسبوعياً | شهرياً | كل عدة شهور |
| **Lead Time for Changes** | <1 ساعة | <1 يوم | <1 شهر | >1 شهر |
| **MTTR** | <1 ساعة | <1 يوم | <1 يوم | >1 أسبوع |
| **Change Failure Rate** | 0-15% | 16-30% | 16-30% | 16-30% |

**هدفنا**: Elite في كل المقاييس خلال سنتين.

### 1.5 فلسفة "Cattle, not Pets"

```
Pets (الطريقة القديمة):
  - كل سيرفر له اسم (db01, web-main)
  - يُعتنى به يدوياً
  - لو مرض، يُعالج
  - فقده كارثة

Cattle (الطريقة الحديثة):
  - السيرفرات أرقام (instance-a4f29)
  - تُدار آلياً
  - لو مرض، يُذبح ويُستبدل
  - الفقد عادي ومتوقع
```

## 2. Infrastructure as Code (IaC)

### 2.1 الفكرة

> **كل البنية التحتية (سيرفرات، شبكات، قواعد بيانات، DNS، صلاحيات) تُعرَّف بكود نصي، يُحفظ في Git، يُراجَع كمرفع.**

### 2.2 الفوائد

```
1. Repeatability    - إعادة إنشاء البيئة بالضبط
2. Version Control  - تاريخ التغييرات
3. Code Review      - كل تغيير يُراجَع
4. Testing          - اختبار البنية
5. Disaster Recovery - إعادة بناء كل شيء بكبسة زر
6. Documentation    - الكود = التوثيق
7. Cost             - حذف الموارد بسهولة
```

### 2.3 الفئات

| الفئة | الأمثلة |
|------|--------|
| **Provisioning** | Terraform, Pulumi, CloudFormation |
| **Configuration** | Ansible, Chef, Puppet |
| **Image Building** | Packer, Docker |
| **Orchestration** | Kubernetes, Docker Swarm |

### 2.4 Declarative vs Imperative

```python
# Imperative - "كيف"
create_vm("vm-1")
create_vm("vm-2")
attach_disk("vm-1", "disk-1")
configure_network("vm-1", "10.0.1.5")

# Declarative - "ماذا"
resources:
  vms:
    - name: vm-1
      disk: disk-1
      ip: 10.0.1.5
    - name: vm-2

# الأداة تكتشف الفرق وتطبّقه
```

> **القاعدة**: Declarative دائماً عندما أمكن.

## 3. Terraform بالتعمق

### 3.1 لماذا Terraform؟

```
- يدعم 1500+ provider (AWS, Azure, GCP, Cloudflare, Datadog, ...)
- Declarative
- مجاني (HCL syntax)
- State management
- Plan قبل Apply
- المعيار الصناعي
```

### 3.2 المكونات الأساسية

```hcl
# providers.tf
terraform {
  required_version = ">= 1.6"
  
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  
  backend "s3" {
    bucket         = "myapp-terraform-state"
    key            = "production/terraform.tfstate"
    region         = "me-south-1"
    encrypt        = true
    dynamodb_table = "terraform-lock"
  }
}

provider "aws" {
  region = var.aws_region
  
  default_tags {
    tags = {
      Project     = "MyAccountingApp"
      Environment = var.environment
      ManagedBy   = "Terraform"
    }
  }
}
```

### 3.4 Modules - إعادة الاستخدام

```hcl
# modules/vpc/main.tf
resource "aws_vpc" "main" {
  cidr_block           = var.cidr_block
  enable_dns_hostnames = true
  enable_dns_support   = true
  
  tags = merge(var.tags, {
    Name = "${var.name}-vpc"
  })
}

resource "aws_subnet" "public" {
  count             = length(var.availability_zones)
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.cidr_block, 8, count.index)
  availability_zone = var.availability_zones[count.index]
  
  map_public_ip_on_launch = true
  
  tags = {
    Name = "${var.name}-public-${count.index}"
    Tier = "public"
  }
}

resource "aws_subnet" "private" {
  count             = length(var.availability_zones)
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.cidr_block, 8, count.index + 10)
  availability_zone = var.availability_zones[count.index]
  
  tags = {
    Name = "${var.name}-private-${count.index}"
    Tier = "private"
  }
}

# الاستخدام
module "production_vpc" {
  source = "./modules/vpc"
  
  name               = "production"
  cidr_block         = "10.0.0.0/16"
  availability_zones = ["me-south-1a", "me-south-1b", "me-south-1c"]
  
  tags = {
    Environment = "production"
  }
}
```

## 4. Pulumi كبديل حديث

### 4.1 الميزة

> **Pulumi: نفس IaC، لكن بلغة برمجة حقيقية (TypeScript, Python, Go, C#).**

### 4.2 مثال

```typescript
import * as aws from "@pulumi/aws";
import * as awsx from "@pulumi/awsx";

// VPC
const vpc = new awsx.ec2.Vpc("main", {
  cidrBlock: "10.0.0.0/16",
  numberOfAvailabilityZones: 3,
  subnets: [
    { type: "public", cidrMask: 24 },
    { type: "private", cidrMask: 20 }
  ]
});

// منطق برمجي - شيء صعب في HCL
const environments = ["dev", "staging", "production"];

environments.forEach(env => {
  const isProd = env === "production";
  
  new aws.rds.Instance(`db-${env}`, {
    engine: "postgres",
    instanceClass: isProd ? "db.r6g.xlarge" : "db.t4g.medium",
    allocatedStorage: isProd ? 100 : 20,
    multiAz: isProd,
    backupRetentionPeriod: isProd ? 30 : 7
  });
});
```

### 4.3 متى Pulumi vs Terraform؟

| الحالة | الأفضل |
|--------|-------|
| فريق DevOps خالص | Terraform |
| فريق developers يديرون البنية | Pulumi |
| منطق معقد، حلقات، شروط | Pulumi |
| توحيد قياسي | Terraform |
| تكاملات أكثر | Terraform |

## 5. Configuration Management (Ansible)

### 5.1 ماذا يفعل Ansible؟

> **بعد إنشاء السيرفر بـ Terraform، Ansible يُهيّئ ما بداخله: تثبيت برامج، إعدادات، خدمات.**

### 5.2 المكونات

```yaml
# inventory.yml
all:
  children:
    webservers:
      hosts:
        web1.example.com:
        web2.example.com:
      vars:
        nginx_workers: 4
    
    databases:
      hosts:
        db1.example.com:
      vars:
        postgres_version: 16
```

### 5.3 Playbook مثال

```yaml
# install-postgres.yml
- name: تثبيت PostgreSQL
  hosts: databases
  become: yes
  
  vars:
    postgres_version: 16
    postgres_data_dir: /var/lib/postgresql/data
  
  tasks:
    - name: إضافة مستودع PostgreSQL
      apt_repository:
        repo: "deb http://apt.postgresql.org/pub/repos/apt {{ ansible_distribution_release }}-pgdg main"
        state: present
    
    - name: تثبيت PostgreSQL
      apt:
        name:
          - "postgresql-{{ postgres_version }}"
          - "postgresql-contrib-{{ postgres_version }}"
        state: present
        update_cache: yes
    
    - name: إعداد postgresql.conf
      template:
        src: postgresql.conf.j2
        dest: "/etc/postgresql/{{ postgres_version }}/main/postgresql.conf"
        owner: postgres
        group: postgres
        mode: '0600'
      notify: restart postgresql
    
    - name: إعداد pg_hba.conf
      template:
        src: pg_hba.conf.j2
        dest: "/etc/postgresql/{{ postgres_version }}/main/pg_hba.conf"
      notify: restart postgresql
    
    - name: التأكد من تشغيل PostgreSQL
      systemd:
        name: postgresql
        state: started
        enabled: yes
    
    - name: إنشاء قاعدة البيانات
      community.postgresql.postgresql_db:
        name: "{{ db_name }}"
        encoding: UTF-8
        lc_collate: en_US.UTF-8
      become_user: postgres
  
  handlers:
    - name: restart postgresql
      systemd:
        name: postgresql
        state: restarted
```

### 5.4 Idempotency

> **Ansible idempotent**: تشغيله 10 مرات = تشغيله مرة واحدة. لو الحالة المطلوبة موجودة، لا يفعل شيئاً.

## 6. Containerization (Docker)

### 6.1 لماذا Containers؟

```
المشكلة القديمة:
  "تعمل عندي" → "لا تعمل عند العميل"
  
الحل: Container
  كل ما يحتاجه التطبيق (كود، dependencies، OS libs) في صندوق واحد.
  يعمل في أي مكان بنفس الطريقة.
```

### 6.2 Container vs VM

```
Virtual Machine                  Container
┌─────────────────┐             ┌─────────────────┐
│   App           │             │   App           │
├─────────────────┤             ├─────────────────┤
│   Libs          │             │   Libs          │
├─────────────────┤             ├─────────────────┤
│   Guest OS      │             │ (shared kernel) │
├─────────────────┤             ├─────────────────┤
│   Hypervisor    │             │   Docker        │
├─────────────────┤             ├─────────────────┤
│   Host OS       │             │   Host OS       │
└─────────────────┘             └─────────────────┘

VM: GB من الذاكرة، دقائق للتشغيل
Container: MB من الذاكرة، ثوانٍ للتشغيل
```

### 6.3 Dockerfile - أفضل الممارسات

```dockerfile
# ❌ سيء - حجم كبير، غير آمن
FROM ubuntu:latest
RUN apt-get update
RUN apt-get install -y nodejs npm
COPY . /app
WORKDIR /app
RUN npm install
CMD npm start

# ✓ جيد - multi-stage، صغير، آمن
# المرحلة 1: Build
FROM node:20-alpine AS builder
WORKDIR /build

# Cache الـ dependencies
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

# Build
COPY . .
RUN pnpm build && pnpm prune --prod

# المرحلة 2: Runtime
FROM node:20-alpine AS runtime

# Security: non-root user
RUN addgroup -g 1001 nodejs && \
    adduser -D -u 1001 -G nodejs nodejs

# انسخ فقط ما نحتاجه
WORKDIR /app
COPY --from=builder --chown=nodejs:nodejs /build/node_modules ./node_modules
COPY --from=builder --chown=nodejs:nodejs /build/dist ./dist
COPY --from=builder --chown=nodejs:nodejs /build/package.json ./

USER nodejs

# Health check
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
    CMD wget --quiet --tries=1 --spider http://localhost:3000/health || exit 1

EXPOSE 3000

# Signal handling صحيح
CMD ["node", "dist/index.js"]
```

## 7. Docker Compose للتطوير

### 7.1 الفائدة

> **بأمر واحد، نُشغّل بيئة كاملة (app + db + cache + queue + monitoring).**

### 7.2 مثال شامل

```yaml
# docker-compose.yml
version: '3.9'

services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
      target: builder              # نستخدم stage الـ builder للتطوير
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/myapp
      REDIS_URL: redis://cache:6379
      NODE_ENV: development
    volumes:
      - .:/app                      # hot reload
      - /app/node_modules           # لا تتجاوز node_modules
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    networks:
      - app-network
    restart: unless-stopped
  
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: myapp
    ports:
      - "5432:5432"
    volumes:
      - postgres-data:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      - app-network
  
  cache:
    image: redis:7-alpine
    command: redis-server --requirepass secret
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
    networks:
```

## 13. CI/CD Pipelines

### 13.1 ما هو CI/CD؟

```
CI (Continuous Integration):
  كل push → بناء + اختبار تلقائي
  
CD (Continuous Delivery):
  CI ينجح → جاهز للنشر (بضغطة زر)
  
CD (Continuous Deployment):
  CI ينجح → ينشر تلقائياً
```

### 13.2 Pipeline نموذجي

```
Push Code
    ▼
Lint (eslint, prettier)
    ▼
Unit Tests
    ▼
Build
    ▼
Integration Tests
    ▼
Security Scan (Snyk, Trivy)
    ▼
Build Container Image
    ▼
Push to Registry
    ▼
Deploy to Staging
    ▼
E2E Tests
    ▼
Performance Tests
    ▼
Manual Approval (للإنتاج)
    ▼
Deploy to Production (Canary)
    ▼
Monitor & Promote (or Rollback)
```

## 14. GitHub Actions بالتعمق

### 14.1 Workflow كامل للإنتاج

```yaml
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # =====================
  # 1. Code Quality
  # =====================
  quality:
    name: Code Quality
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - uses: pnpm/action-setup@v2
        with:
          version: 8
      
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'
      
      - name: Install dependencies
        run: pnpm install --frozen-lockfile
      
      - name: Lint
        run: pnpm lint
      
      - name: Format check
        run: pnpm format:check
      
      - name: Type check
        run: pnpm typecheck

  # =====================
  # 2. Tests
  # =====================
  test:
    name: Tests
    runs-on: ubuntu-latest
    
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
        ports:
          - 5432:5432
      
      redis:
        image: redis:7
        ports:
          - 6379:6379
    
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v2
        with: { version: 8 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: 'pnpm' }
      
      - run: pnpm install --frozen-lockfile
      
      - name: Unit tests
        run: pnpm test:unit --coverage
      
      - name: Integration tests
        run: pnpm test:integration
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/test
          REDIS_URL: redis://localhost:6379
      
      - name: Upload coverage
        uses: codecov/codecov-action@v3

  # =====================
  # 3. Security
  # =====================
  security:
    name: Security Scan
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Dependency audit
        run: pnpm audit --audit-level=high
      
      - name: Snyk scan
        uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
      
      - name: Detect secrets
        uses: trufflesecurity/trufflehog@main
        with:
          path: ./
          base: ${{ github.event.repository.default_branch }}
      
      - name: SAST with Semgrep
        uses: returntocorp/semgrep-action@v1
        with:
          config: p/owasp-top-ten

  # =====================
  # 4. Build Image
  # =====================
  build:
    name: Build Image
    needs: [quality, test, security]
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    
    outputs:
      image: ${{ steps.meta.outputs.tags }}
      digest: ${{ steps.build.outputs.digest }}
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3
      
      - name: Set up Buildx
        uses: docker/setup-buildx-action@v3
      
      - name: Login to Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      
      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
            type=sha,format=long
      
      - name: Build and push
        id: build
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          platforms: linux/amd64,linux/arm64
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
      
      - name: Scan image
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ steps.meta.outputs.tags }}
          format: 'sarif'
          output: 'trivy-results.sarif'
          severity: 'CRITICAL,HIGH'
          exit-code: '1'
      
      - name: Sign image
        run: |
          cosign sign --yes ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ steps.build.outputs.digest }}
        env:
          COSIGN_EXPERIMENTAL: 1

  # =====================
  # 5. Deploy Staging
  # =====================
  deploy-staging:
    name: Deploy to Staging
    needs: build
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.myapp.com
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup kubectl
        uses: azure/setup-kubectl@v3
      
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE }}
          aws-region: me-south-1
      
      - name: Update kubeconfig
        run: aws eks update-kubeconfig --name staging-cluster
      
      - name: Deploy with Helm
        run: |
          helm upgrade --install myapp ./helm/myapp \
            --namespace staging \
            --set image.tag=${{ github.sha }} \
            --values ./helm/myapp/values.staging.yaml \
            --wait \
            --timeout 5m
      
      - name: Run smoke tests
        run: ./scripts/smoke-tests.sh https://staging.myapp.com

  # =====================
  # 6. Deploy Production
  # =====================
  deploy-production:
    name: Deploy to Production
    needs: build
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://api.myapp.com
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Deploy Canary (10%)
        run: |
          helm upgrade --install myapp-canary ./helm/myapp \
            --namespace production \
            --set image.tag=${{ github.sha }} \
            --set canary.enabled=true \
            --set canary.weight=10
      
      - name: Monitor canary (10 minutes)
        run: |
          ./scripts/monitor-canary.sh --duration 600 --threshold-error-rate 1
      
      - name: Promote to 50%
        run: |
          helm upgrade myapp-canary ./helm/myapp \
            --reuse-values \
            --set canary.weight=50
      
      - name: Monitor (5 minutes)
        run: |
          ./scripts/monitor-canary.sh --duration 300 --threshold-error-rate 1
      
      - name: Full deployment
        run: |
          helm upgrade --install myapp ./helm/myapp \
            --namespace production \
            --set image.tag=${{ github.sha }} \
            --values ./helm/myapp/values.production.yaml \
            --wait
      
      - name: Cleanup canary
        run: helm uninstall myapp-canary --namespace production
      
      - name: Notify team
        uses: 8398a7/action-slack@v3
        with:
          status: ${{ job.status }}
          fields: repo,message,commit,author,action
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK }}
```

## 16. Database Migrations في الإنتاج

### 16.1 الخطر

> **migration واحد سيء = توقف 6 ساعات.**

### 16.2 القواعد الذهبية

```
1. Migrations يجب أن تكون backward compatible
2. لا تحذف عمود مباشرة → mark deprecated → احذف لاحقاً
3. لا تُعد تسمية عمود → أضف جديد، انسخ، احذف القديم
4. لا تُقفل جدول كبير → استخدم online migration
5. لكل migration يجب أن يكون له rollback
6. اختبر على نسخة من الإنتاج أولاً
```

### 16.3 Migration Pattern: Expand-Contract

```
أردنا تغيير عمود `name` إلى `full_name`:

❌ خطر:
ALTER TABLE users RENAME COLUMN name TO full_name;
(يكسر التطبيق القديم)

✓ آمن (3 مراحل):

Phase 1: Expand
  ALTER TABLE users ADD COLUMN full_name VARCHAR;
  UPDATE users SET full_name = name;
  CREATE TRIGGER sync_names ... (يُبقي الاثنين متزامنين)
  
  Deploy code يستخدم كليهما (read both, write both)

Phase 2: Migrate
  Deploy code يكتب لـ full_name فقط، يقرأ من full_name
  
Phase 3: Contract
  DROP TRIGGER sync_names;
  ALTER TABLE users DROP COLUMN name;
```

### 16.4 أدوات

- **Flyway** (Java/SQL)
- **Liquibase** (XML/SQL/YAML)
- **Prisma Migrate** (Node)
- **Alembic** (Python)
- **golang-migrate** (Go)

### 16.5 مثال بـ Prisma

### 16.6 Zero-Downtime Migration Script


### 20.4 Self-Hosted Flag Service

```typescript
// خدمة بسيطة بـ Redis
class FeatureFlagService {
  async isEnabled(flag: string, context: Context): Promise<boolean> {
    const config = await this.getFlagConfig(flag);
    
    if (!config.enabled) return false;
    
    // Targeted users
    if (config.targetedUsers.includes(context.userId)) return true;
    
    // Percentage rollout (consistent hashing)
    const hash = crc32(`${flag}-${context.userId}`);
    const userPercentage = hash % 100;
    
    return userPercentage < config.rolloutPercentage;
  }
}
```

```

3. لا تستخدم flags كـ if/else دائم → مديونية تقنية
4. اختبر كل المسارات (مع flag مفعل + معطل)
5. راقب الـ flags في الـ logs
```

## 21. A/B Testing Infrastructure

### 21.1 الفكرة

```
50% من المستخدمين → نسخة A (control)
50% من المستخدمين → نسخة B (treatment)

نقيس: أيهما يحقق نتائج أفضل (نسبة شراء، وقت بقاء، إلخ)
```

### 21.2 المكونات

```
1. Assignment Service  → يحدد user أي variant
2. Tracking Service    → يسجل الأحداث
3. Analytics           → تحليل النتائج
4. Statistical Engine  → هل النتائج significant؟
```

### 21.3 Implementation

```typescript
class ABTestingService {
  async getVariant(experimentId: string, userId: string): Promise<string> {
    const experiment = await this.getExperiment(experimentId);
    
    if (!experiment.active) return 'control';
    
    // Consistent assignment (نفس المستخدم = نفس variant دائماً)
    const hash = crc32(`${experimentId}-${userId}`);
    const bucket = hash % 100;
    
    let cumulative = 0;
    for (const variant of experiment.variants) {
      cumulative += variant.percentage;
      if (bucket < cumulative) {
        // Track assignment
        await this.trackEvent('experiment.assigned', {
          experimentId,
          variant: variant.name,
          userId
        });
        return variant.name;
      }
    }
    
    return 'control';
  }
  
  async trackConversion(experimentId: string, userId: string, metric: string, value: number) {
    await this.trackEvent('experiment.conversion', {
      experimentId,
      userId,
      metric,
      value
    });
  }
  
  async analyzeResults(experimentId: string): Promise<AnalysisResult> {
    const results = await this.fetchResults(experimentId);
    
    // Chi-square test أو t-test
    const significance = this.calculateSignificance(results);
    
    return {
      winner: significance.winner,
      confidence: significance.confidence,
      sampleSize: results.sampleSize,
      isSignificant: significance.confidence > 0.95
    };
  }
}
```

### 22.2 Read/Write Splitting

```typescript
class DatabaseRouter {
  private writeDb = new Pool({ host: 'primary.db.aws.com' });
  private readDbs = [
    new Pool({ host: 'replica-1.db.aws.com' }),
    new Pool({ host: 'replica-2.db.aws.com' }),
    new Pool({ host: 'replica-3.db.aws.com' })
  ];
  
  async write(query: string, params: any[]) {
    return await this.writeDb.query(query, params);
  }
  
  async read(query: string, params: any[]) {
    // Round-robin
    const replica = this.readDbs[Math.floor(Math.random() * this.readDbs.length)];
    return await replica.query(query, params);
  }
}
```

### 23. CDN & Edge Computing

#### CDN Strategy

```

  → CloudFront / Cloudflare
  → Cache forever (with versioned URLs)

API Responses:
  → Cache GETs (with proper headers)
  → Cache-Control: public, max-age=300
  → CDN-Cache-Control: s-maxage=3600

Dynamic Content:
  → No cache
  → Direct to origin
```

## 28. SLO/SLI/SLA Management

### 28.1 المفاهيم

```
SLI (Service Level Indicator):
  ما نقيسه فعلياً
  مثال: نسبة الطلبات الناجحة
  
SLO (Service Level Objective):
  هدفنا الداخلي
  مثال: 99.9% من الطلبات تنجح
  
SLA (Service Level Agreement):
  التعهد للعميل (مع غرامات)
  مثال: 99.5% uptime، أو نُعوّض

دائماً: SLA < SLO < فعلي
```

### 28.2 Error Budget

```
SLO = 99.9% → Error budget = 0.1%
  = 43.8 دقيقة توقف مسموح/شهر
  
لو استهلكنا 30 دقيقة → باقي 13.8 دقيقة
  → نتوقف عن نشر features جديدة
  → نركز على الـ reliability

لو لم نستهلك شيئاً → نستطيع المخاطرة أكثر
  → نشر features جريئة
```

### 28.3 Tracking

```promql
# SLI: نسبة الطلبات الناجحة في الشهر
sum(rate(http_requests_total{status!~"5.."}[30d])) 
/ sum(rate(http_requests_total[30d]))

# Error budget remaining
1 - ((1 - 0.999) - (1 - sli)) / (1 - 0.999)
```

## 30. Chaos Engineering

### 30.1 الفكرة

> **اكسر النظام عمداً في الإنتاج. تأكد أنه يصمد. لو لم يصمد، أصلحه قبل أن يحدث بالصدفة.**

ابتكرتها Netflix بـ Chaos Monkey.

### 30.2 المبادئ

```
1. ابدأ بـ steady state - حدد كيف يبدو "صحي"
2. فرضية - ماذا تتوقع لو حدث X؟
3. ابدأ صغيراً - بيئة dev أولاً
4. توسع تدريجياً - staging ثم production
5. أتمت - تجارب يومية
6. تعلم - وثّق كل failure
```

### 30.3 أنواع التجارب

```
1. Resource Exhaustion
   - استهلك 90% CPU
   - استهلك 90% Memory
   - استهلك 90% Disk
   - استهلك 90% Network

2. Network
   - أضف latency
   - أسقط packets
   - قطع الاتصال بين خدمات

3. Application
   - رد بـ 500 errors
   - تأخير الردود
   - أرسل بيانات مكسورة

4. Infrastructure
   - أوقف instance
   - أوقف availability zone
   - أوقف region

5. Time
   - غيّر الوقت في النظام
   - clock skew بين السيرفرات
```

### 30.4 أدوات

- **Chaos Mesh** - الأفضل لـ K8s
- **Litmus** - K8s
- **Gremlin** - مُدار
- **AWS Fault Injection Simulator**

### 30.5 مثال: Chaos Mesh


## 31. Backup & Recovery Automation

### 31.1 3-2-1 Rule

```
3 نسخ من البيانات (الأصل + 2 backups)
2 وسائط مختلفة (disk + cloud)
1 خارج الموقع (off-site)
```

### 31.2 Automated Backup

```yaml
# K8s CronJob للـ backup اليومي
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postgres-backup
spec:
  schedule: '0 2 * * *'        # 2 AM كل يوم
  
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: backup
              image: postgres:16-alpine
              command:
                - /bin/sh
                - -c
                - |
                  set -e
                  TIMESTAMP=$(date +%Y%m%d_%H%M%S)
                  
                  # 1. Backup
                  pg_dump $DATABASE_URL | gzip > /tmp/backup_$TIMESTAMP.sql.gz
                  
                  # 2. Encrypt
                  openssl enc -aes-256-cbc -salt -pbkdf2 -iter 100000 \
                    -in /tmp/backup_$TIMESTAMP.sql.gz \
                    -out /tmp/backup_$TIMESTAMP.sql.gz.enc \
                    -pass env:BACKUP_PASSWORD
                  
                  # 3. Upload to S3
                  aws s3 cp /tmp/backup_$TIMESTAMP.sql.gz.enc \
                    s3://backups/postgres/$TIMESTAMP.sql.gz.enc
                  
                  # 4. Cross-region replication (تلقائي على S3)
                  
                  # 5. Verify
                  aws s3 ls s3://backups/postgres/$TIMESTAMP.sql.gz.enc
                  
                  # 6. Notify
                  curl -X POST $SLACK_WEBHOOK \
                    -d "{\"text\": \"Backup completed: $TIMESTAMP\"}"
          
          restartPolicy: OnFailure
```

### 31.3 Backup Testing

> **النسخة الاحتياطية غير المختبرة = لا نسخة.**

```bash
# كل أسبوع، نختبر الاستعادة
#!/bin/bash

# 1. أنشئ DB مؤقتة
createdb test_restore_$(date +%s)

# 2. استعد آخر backup
LATEST=$(aws s3 ls s3://backups/postgres/ | sort | tail -1 | awk '{print $4}')
aws s3 cp s3://backups/postgres/$LATEST /tmp/

# 3. فك التشفير
openssl enc -d -aes-256-cbc -pbkdf2 -iter 100000 \
  -in /tmp/$LATEST \
  -out /tmp/backup.sql.gz \
  -pass env:BACKUP_PASSWORD

# 4. استعد
gunzip -c /tmp/backup.sql.gz | psql test_restore_$(date +%s)

# 5. تحقق
psql test_restore -c "SELECT COUNT(*) FROM users;"

# 6. احذف
dropdb test_restore_$(date +%s)

# 7. أبلغ
echo "Backup test passed"
```

### 32.3 OIDC (الأفضل)

بدلاً من تخزين AWS keys في GitHub:

```yaml
permissions:
  id-token: write          # لـ OIDC

steps:
  - name: Configure AWS
    uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123:role/GitHubActions

```

### 32.4 Sealed Secrets في K8s

```bash
# المطور يكتب secret عادي
echo -n "mypassword" | kubectl create secret generic mysecret --dry-run=client --from-file=password=/dev/stdin -o yaml > secret.yaml

# يُشفّره
kubeseal -f secret.yaml -w sealed-secret.yaml

# الآن sealed-secret.yaml آمن للـ commit
# فقط الـ cluster يستطيع فكه
```

```rego
package kubernetes.admission

deny[msg] {

  not container.resources.limits.memory
  msg := sprintf("Container %s must have memory limit", [container.name])

  input.request.kind.kind == "Pod"
  container := input.request.object.spec.containers[_]
  container.image
  not startswith(container.image, "myregistry.com/")

}

deny[msg] {
  input.request.kind.kind == "Pod"
```
